# MariaDB 11.8 activation failure — diagnosis from code evidence (2026-10-20)

Status: **DIAGNOSED, NOT RUN on a real 11.8 server.** No 11.8 execution was possible in
this environment (no Docker/root, no database service), so no 11.8 compatibility is
claimed. A precise reproducible test is given in §4.

## 1. Evidence actually collected

| Evidence | Source | Result |
|---|---|---|
| Pinned database lanes in this repository | `.github/workflows/ci.yml` (`mariadb:11.4.13`, MySQL 8.4.11 in first-practice acceptance), `.github/workflows/first-practice-acceptance.yml`, `.github/workflows/mariadb-10.11-compat.yml` (`mariadb:10.11.19@sha256:bb27bde…`) | Only MySQL 8.x, MariaDB 11.4.13 and MariaDB 10.11.19 are ever executed. **No lane runs 11.8.** |
| Engine gate in migration 0027 | `src/Migrations/2026_10_13_0027_custom_role_archival.php`, lines ~40–52 | Version whitelist `\A(?:10\.11\.\d+|11\.4\.13)(?:-MariaDB)?…` for MariaDB, `\A8\.\d+\.\d+…` for MySQL; anything else **throws** `migration 0027: unsupported database server; expected MySQL 8, MariaDB 10.11.x, or MariaDB 11.4.13`. |
| Behavior of that exact pattern on real 11.8 version strings | Executed locally against the literal pattern copied from the source | `10.11.19-MariaDB-ubu2404` → match; `11.4.13-MariaDB-log` → match; `11.8.2-MariaDB`, `11.8.2-MariaDB-ubu2404`, `11.8.0-MariaDB-deb12` → **no match**. |

## 2. Root cause (deduced, high confidence)

Plugin activation runs the migration chain. On MariaDB 11.8, migration 0027's engine
gate cannot classify the server (the whitelist predates 11.8), so it throws by design
(fail closed). Activation therefore aborts **before** any schema change with
`migration 0027: unsupported database server; expected MySQL 8, MariaDB 10.11.x, or
MariaDB 11.4.13`. This is a deliberate guard rejecting an unvalidated engine, not a
schema-incompatibility bug — but from an operator's point of view it is still an
activation failure, and it will reproduce deterministically on every 11.8 server.

Not established by evidence: whether MariaDB 11.8 would otherwise accept the 0027
CHECK/ENUM metadata paths. MariaDB 11.8's `CHECK_CONSTRAINTS` and
`@@session.check_constraint_checks` behavior is expected to follow the 10.11/11.4
family, but that expectation is **unverified here** and must not be treated as a
compatibility claim.

## 3. Why no code change was made in this slice

Extending the whitelist to `11.8.x` without executing a real 11.8 install would convert
a fail-closed guard into an unverified compatibility claim, on a schema-changing
migration path. The Owner's release rule forbids that. The decision is therefore left
to an explicit follow-up: (a) run §4, (b) if the metadata assertions pass, extend the
pattern and add a pinned 11.8 lane next to the 10.11 lane, (c) if they fail, keep the
guard and document the supported ceiling.

## 4. Reproducible test (the exact check an isolated installer must run)

```bash
# 1. Real server
docker run -d --name cpms-mdb118 -e MARIADB_ROOT_PASSWORD=root -p 3318:3306 mariadb:11.8
until docker exec cpms-mdb118 mariadb -uroot -proot -e 'SELECT VERSION()' >/dev/null 2>&1; do sleep 2; done

# 2. Prove the gate's input string
docker exec cpms-mdb118 mariadb -uroot -proot -N -e \
  "SELECT VERSION(), @@version_comment, @@session.check_constraint_checks"

# 3. Prove the gate rejects it (expected: RuntimeException, activation blocked)
php -r '$v = trim(shell_exec(...)); // paste the VERSION() value
$re = "/\A(?:10\.11\.\d+|11\.4\.13)(?:-MariaDB)?(?:[-+][a-zA-Z0-9._-]+)?\z/i";
var_dump(preg_match($re, $v));'

# 4. Isolated WordPress + plugin activation (never against a live site)
wp core download --path=/tmp/wp118 --version=7.1.3
wp config create --path=/tmp/wp118 --dbname=cpms118 --dbuser=root --dbpass=root --dbhost=127.0.0.1:3318
wp core install --path=/tmp/wp118 --url=http://localhost:8080 --title=CPMS118 --admin_user=admin \
  --admin_password=secret --admin_email=admin@example.test --skip-email
wp plugin activate clinic-practice-management --path=/tmp/wp118   # expect: activation error from 0027
wp cpms migrate --path=/tmp/wp118                                  # if the above aborts: capture the RuntimeException

# 5. Idempotent replay once the gate accepts the server
wp cpms migrate --path=/tmp/wp118   # second run must be a no-op (head unchanged, no error)
wp cpms status --path=/tmp/wp118    # must report migration head 2026_10_13_0027

# 6. Metadata parity probes (the only thing that can justify widening the gate)
docker exec cpms-mdb118 mariadb -uroot -proot cpms118 -e \
  "SELECT TABLE_NAME, CONSTRAINT_NAME FROM information_schema.CHECK_CONSTRAINTS
    WHERE CONSTRAINT_SCHEMA = 'cpms118' AND TABLE_NAME LIKE '%custom_role_defs';"
```

Pass criteria for widening the gate: step 3 shows the version string, step 4/5 complete
with `check_constraint_checks = 1`, step 5 is an idempotent no-op, step 6 returns the
0027 CHECK constraint exactly once. Until all four hold on a real 11.8 server, MariaDB
11.8 remains **unsupported and NOT RUN**.

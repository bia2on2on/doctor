|---|---|

Stream bounded chunks; check disk capacity, quotas and configurable timeout, abort incomplete output and clean restricted staging. No whole SQL/file read into memory. |

## 4. Encryption, signatures and custody

| Element | Design |
|---|---|
| Setup | Generate encryption keypair and Ed25519 signing keypair. Site retains encryption public key and protected signing secret; doctor's offline, versioned key bundle holds encryption private/public key and signing public key, key IDs and format. The signing secret is deliberately host-resident under D-C, not included in backups. Protect the entire bundle, including signing public key, encryption keys, key IDs and format, with phrase-derived AEAD; bind the clear version, salt, bounded KDF parameters and nonce as AEAD associated data. Derive the wrapping key with Argon2id and the independently held recovery phrase; verify the bundle authentication before trusting any metadata or signing key. Wrong phrase, altered metadata/ciphertext or failed authentication rejects the bundle and restore; do not substitute a key from the archive. See [PHP Argon2](https://www.php.net/manual/en/function.sodium-crypto-pwhash.php). Securely deliver and test the bundle/phrase off-host; no phrase or key in logs. |
| Backup | Per backup generate a random data key, seal it to the encryption public key; stream authenticated XChaCha20-Poly1305 secretstream chunks, requiring final tag and no trailing bytes. Hash the exact canonical versioned header plus ciphertext incrementally with SHA-256; sign a domain-separated header+digest using Ed25519 detached signature. Signature is over ciphertext, not a loaded whole archive. [Sealed box](https://www.php.net/manual/en/function.sodium-crypto-box-seal.php) gives confidentiality/integrity, not sender identity; [secretstream](https://www.php.net/manual/en/function.sodium-crypto-secretstream-xchacha20poly1305-init-push.php), [sign](https://www.php.net/manual/en/function.sodium-crypto-sign-detached.php), [verify](https://www.php.net/manual/en/function.sodium-crypto-sign-verify-detached.php). |
| Restore | Manager supplies independently trusted bundle and phrase. Verify the signature over the bounded, streamed archive first with the bundle's signing public key, before decrypting. Do not trust an embedded signing key. Then unwrap data key, authenticate every chunk and final tag and manifest/digests. Require sodium functions at both ends; absent extension = fail closed, install supported sodium, no plaintext fallback. |
| Lifecycle | Create local encrypted output directly; do not write decrypted SQL or another plaintext dump file to disk. During restore feed authenticated chunks from memory into database staging; attachments use private temporary files as specified in §5. LIMITATION: database and private attachment storage may contain plaintext identity data; deletion of files on SSDs, snapshots, swap, DB logs and backups is not guaranteed. Protect these at least as strongly as the live site; disable application/driver query-parameter logging for restore and exclude identity values from restore logs, errors and reports. Database-managed journals and host snapshots remain subject to the live-site protection and retention policy. Reuse secretstream concepts from existing envelope but migrate S3 to mirror the same signed encrypted container, not a host-key-encrypted plaintext local backup. Legacy import requires separate explicitly approved migration and old key; no silent downgrade. |
| Loss and rotation | Loss of bundle or phrase makes protected private key unavailable unless separately secured recovery copies exist. Loss of signing public key prevents trusted verification; loss of signing secret prevents new signatures, not old verification. Rotate keys with explicit manager enrollment and new bundle; retain prior bundles to read historical backups. Losing only the host must not lose the doctor's backup and bundle. Live-host compromise can forge future signatures; show signed sequence/time and request manager confirmation against independent records. Anti-rollback is manual, not automatic. |

## 5. Restore, barrier, audit and rollback

| Phase | Required behavior |
|---|---|
| Preflight | Fresh independent WP + compatible CPMS install, no clinical data and no conflicting CPMS users beyond a designated recovery manager; reject collisions, unsupported prefix, multisite or incompatible schema/engines. Validate full signature, decrypt/verify entire archive and manifest in bounded memory, paths, per-file digests, schema census, mappings, disk space and version matrix before target data changes; a prior failed attempt is cleaned up under its closed barrier before retry validation. Fresh WP requires an empty CPMS dataset, not an absent WP administrator. Recheck emptiness after locking. Reject unrecognized SQL/identifiers; use structured table records and allowlisted identifiers, not blind text prefix replacement. |
| Close | Set durable non-autoloaded WP option **before** writes, confirm read-back, lock restore, drain active requests; option is outside the CPMS dump selection (`BackupSqlDumper.php:113-118`) and excluded from plugin-option import. A missing/unreadable barrier state during recovery fails closed. Deny patient access levels, login, staff/API/CLI/cron/jobs and file delivery; allow only separately authenticated, capability-checked recovery manager route. Protect files outside webroot and enforce barrier at early entry points. Restart/failure retains barrier. Bootstrap and server-level bypass coverage is a release blocker. |
| Stage | Create target-prefix staging tables in the same database with the same access and at-rest protections as live tables. Decrypt secretstream chunks in memory and feed records directly to staging, with no plaintext SQL or dump file. On failure and at the start of the next attempt, drop restore-owned staging tables under the closed barrier; if cleanup fails, keep closed and require recovery. Decrypt each attachment to a private temporary name outside webroot, verify its digest, then move to its final private location under the barrier; Track restore-owned final names in the journal; remove temporary names and unpublished restore-owned final files on failure and the next attempt. After a swap, identify published versus staging names before cleanup; do not drop renamed live tables or unrelated files. If cleanup or ownership is uncertain, keep the barrier closed. Check each query and result (including metadata, DDL, writes and commit); strict errors, never increment success after false. OBSERVED: `src/Infrastructure/Db/CpmsDb.php:17-25,109-119` defaults to soft false; `BackupService.php:348-360` ignores results. Create target WP users with fresh IDs and explicit mapping, remap L columns/known live embedded references. Preserve the imported password hash exactly for its mapped user, without treating it as a plaintext password or hashing it again; the verified import mechanism is a release prerequisite. On a later sign-in, WordPress [wp_check_password](https://developer.wordpress.org/reference/functions/wp_check_password/) checks the entered password against that hash in memory, without storing the raw password. [wp_insert_user](https://developer.wordpress.org/reference/functions/wp_insert_user/) documents plaintext input for new users, so passing a saved hash as the new-user password would rehash it; do not do that. Test supported WP versions and pluggable hash implementations; reject unsupported hash formats rather than silently lock users out. Fail unresolved/deleted users, collisions or unsupported data; do not bind source IDs to unrelated target users. Preserve H IDs. Import role capabilities carefully without importing foreign sessions or privileges. Stage files and rewrite root configuration. |
| Publish | Run staging integrity checks then one multi-table `RENAME TABLE` swap for the supported engine/configuration, after validating FK names/constraints and privileges. MySQL documents atomic rename under its stated conditions: [RENAME TABLE](https://dev.mysql.com/doc/refman/8.0/en/rename-table.html). DDL is not treated as transactional across filesystem, WP users and options; barrier spans every phase. On any failure leave closed, retain the non-sensitive journal, drop restore-owned staging tables and clean restore-owned file names as in §5, and offer explicit retry or teardown of disposable fresh target; no claim of automatic rollback. A crash during swap is diagnosed by persisted journal and object census before retry. |
| Audit | OBSERVED: `src/Infrastructure/Audit/HashChain.php:22-27,50-61` hashes previous hash and canonical clinic_id, actor_wp_user_id, actor_role, action, resource_type/id, patient_id, ip_hash, session_id, request_id, created_at; before/after/meta are excluded (`:30-32`). Restore existing audit rows byte-identically, including source actor IDs; verify full chain before and after import. Never treat historical actor IDs as live authority. Append exactly one `restore performed` event with backup ID/date, plugin version, mapping digest and counts. Store mapping in an access-controlled, encrypted restore-report artifact, not a new table. Verify appended chain. |
| Reauthorization | Manager decision D-B: force patient login rows, including future `cpms_patient_logins`, to closed/needs-manager-review semantics; invalidate WP sessions, OTP, reset tokens and outstanding credentials. Staff memberships are disabled pending individual manager reconfirmation. Reconfirm staff and patient accounts independently against trustworthy current evidence; do not infer later revocations from a snapshot. Barrier remains until verification passes and explicit manager acceptance. Acceptance does not bulk-enable accounts: unreviewed or revoked users stay denied. After restore, patient logins start closed. Following the barrier clearance and required individual review against current revocation evidence, patients re-establish access through the new PR #354 mobile + SMS OTP + national-ID flow: owner policy grants full access to their own record when both factors match that record. OTP possession alone grants no full access, a mismatch grants no full access, and a revoked account stays denied unless independent current evidence and authorized review establish that it is eligible for re-establishment; a confirmed current revocation remains denied. No previously issued session, OTP or token is revived. If a schema has no closed state, use a fail-closed option-backed review registry initialized to deny before publish and consulted at every login and access decision even after the global barrier clears, or block release pending identity coordination; no silent activation. The registry must survive restarts and failed option reads must deny access. |

INFERENCE (adversarial review): manager action is security-sensitive; require an independently provisioned recovery manager and avoid granting a restored staff user recovery authority merely because source IDs collide. The recovery route must permit individual review while the barrier is set, but cannot serve patient records/files to other callers; failed or incomplete user review stays denied after global acceptance. Archive ciphertext must be protected from replacement between validation and apply: hold an immutable private file descriptor/copy and revalidate its digest immediately before use. Restore acceptance must not depend on successful cleanup of a temporary fixture granting privileges; synthetic isolation checks run in a separate disposable install or a tightly controlled transaction with verified cleanup. A failure in cleanup keeps the barrier closed.

OBSERVED: booking copies a user-supplied reason into an appointment and passes its view to audit (`src/Application/Booking/BookingService.php:1015-1027,1056-1065,3367-3382`); the audit sanitizer matches sensitive **keys**, not arbitrary reason values (`src/Infrastructure/Audit/AuditLogger.php:24-26,241-261`). Historical audit reason text MAY contain a national ID entered as free text; UNKNOWN how many. D-A remains: restore historical audit rows byte-identically; the encrypted backup and restored data require the same care as the live database. After restore, an INFORMATIONAL report counts audit rows whose reason text matches a ten-digit pattern, once per row, without displaying, logging or exporting the matching values; a count is not proof of national IDs. Scan reason fields in `before_json`/`after_json`/`meta_json` in memory; on scan error show count UNKNOWN, not a failed restore. Manager requires the identity build P2 prerequisite to remove booking free text from new audit writes. LIMITATION: the current PR #354 P2 describes `PATIENT_CREATED` audit redaction; extending that prerequisite to booking free text requires coordination and verification, not an assertion that it is already implemented.
